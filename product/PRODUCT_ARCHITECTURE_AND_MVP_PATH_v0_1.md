# General Live Cash System — Product Architecture and MVP Path v0.1

Status: `PRODUCT_HYPOTHESIS_ARCHITECTURE`

Purpose: separate the private research corpus from a future original commercial learning product.

## Product thesis

The product is not a summary of poker courses.

The product helps a player convert live-cash theory into repeatable decisions under time pressure through:

- compact heuristics;
- decision algorithms;
- misconception diagnosis;
- adaptive drills;
- opponent-model calibration;
- session-to-study feedback.

## Primary initial user

A competent poker player, often with tournament or online experience, who:

- understands basic poker vocabulary;
- struggles with live-cash depth, OOP play, 3-bet pots or multiway pots;
- does not want to memorize hundreds of charts;
- wants a clear daily study route;
- needs transfer from study to real sessions.

## Product layers

# Layer 0 — Private research corpus

Contains:

- paid-course transcripts;
- source-specific analyses;
- visual notes;
- internal provenance;
- contradiction work;
- rerun evidence.

Never distributed to customers.

# Layer 1 — Original knowledge model

Contains independently written:

- heuristics;
- algorithms;
- misconception taxonomy;
- opponent and environment schemas;
- admission status;
- original examples;
- independently validated anchor ranges.

This is the core intellectual asset.

# Layer 2 — Learning engine

Functions:

- initial diagnostic;
- daily micro-session;
- drill selection;
- spaced repetition;
- reasoning-level feedback;
- variant generation;
- mastery tracking;
- regression detection.

# Layer 3 — Session companion

Functions:

- pre-session cues;
- lightweight uncertain-hand capture;
- post-session reconstruction;
- misconception diagnosis;
- repair-drill assignment;
- player and environment evidence update.

# Layer 4 — Deployment profiles

Examples:

- 100bb casino cash;
- deep $2/$5;
- high-rake $1/$3;
- straddled loose-passive game;
- short-stack-heavy lineup;
- Batumi field profile.

Profiles change prioritization and exploit weighting, not the general core.

# Layer 5 — Advanced tools

Possible later components:

- solver-backed original scenario generation;
- hand-history import;
- voice-based hand capture;
- personalized opponent notebook;
- coach/reviewer dashboard;
- Sharky integration;
- group/cohort analytics.

## User-facing product objects

### Heuristic card

A compact ordered reasoning sequence for a domain.

- retest family.

### Opponent profile

- branch-specific read;
- confidence;

- node;
- action;

- game structure;

## MVP 0 — Manual personal system

No software required.

Deliverables:

- provisional Playbook;
- 20-session learning route;
- Markdown/spreadsheet drill queue;
- session review template;
- opponent notes;
- environment profile.

Success test:

- learner actually uses it for several sessions;
- recurring misconceptions become visible;
- study priorities change from evidence;
- table cues are recalled in time.

## MVP 1 — Structured prototype

Possible implementation:

- simple web or mobile interface;
- 8 initial drill packs;
- 14–18 admitted heuristics;
- daily review queue;
- manual hand capture;
- mastery and misconception tracking.

No solver integration required.

Success test:

- users complete repeated sessions;
- delayed retention improves;
- correct action for wrong reason is detected;
- users can connect a live hand to a trained mechanism.

## MVP 2 — Closed beta

Add:

- multiple environment profiles;
- adaptive difficulty;
- original scenario library;
- session evidence dashboard;
- field-validation analytics;
- content-purity review.

Suggested beta cohort:

- tournament-to-cash converts;
- recreational/serious $1/$3–$2/$5 players;
- mix of 100bb and deep-stack environments.

## MVP 3 — Commercial product

Requirements before launch:

- independent IP/legal review;
- original or licensed visuals;
- independently validated ranges;
- content that does not require paid-course access;
- reliable onboarding diagnostic;
- clear scope and responsible-gambling framing;
- customer support and correction process.

## Product differentiation

The differentiator is not more poker information.

It is:

`SOURCE COMPLEXITY → ORIGINAL COMPRESSION → DIAGNOSIS → PRACTICE → FIELD EVIDENCE`

The system should answer:

- What should I learn next?
- Why did I make this mistake?
- What cue can I recall at the table?
- Which variant proves I understand the mechanism?
- How should this game environment change my priorities?

## Non-goals

- reproduce paid courses;
- become a giant static chart library;
- promise guaranteed win rate;
- prescribe exact exploits from weak evidence;
- replace responsible bankroll and game-selection decisions;
- build software before the manual learning loop is validated.

## IP boundary

Commercial layer must contain only:

- independently written rules;
- original examples;
- original drill structures;
- independently generated or licensed charts/visuals;
- internal provenance without redistribution of source material.

## Sharky relationship

Live Cash System owns:

- domain research;
- canonical poker mechanisms;
- evidence and scope;
- opponent/environment models.

Sharky may own:

- interactive lesson presentation;
- diagnostic UX;
- repair loops;
- progression and motivation;
- learner-facing visualization.

Only source-pure, admitted content crosses the boundary.
