# Live Cash System — Agent Operating Contract

Scope: entire repository.

## Bootstrap

Before doing substantive work:

1. verify the live default branch and current `main` state;
2. read `START_HERE.md`;
3. read `state/CURRENT_PROJECT_STATE.yaml`;
4. read `PROJECT_ATLAS.md`;
5. open only the active source registry, latest terminal report and affected authority files;
6. state the active milestone and the bounded next move.

Do not restart project diagnosis when the repository already contains an accepted checkpoint.

## Primary objective

Build a compact, adaptive and interactive live-cash learning system for a strong MTT player preparing for live `1/3` and `2/5`, usually `100–200bb`, sometimes deeper, with straddles and short effective stacks possible.

The final system should prefer:

- a small robust rule core;
- compact decision trees;
- original anchor ranges;
- adaptive micro-lessons;
- prediction before feedback;
- action/reason/confidence separation;
- spaced retrieval;
- live field transfer.

## Source purity

Canonical source records must preserve what the source actually says, including uncertainty and hedging.

Never silently:

- repair a disputed card, size or frequency from general poker knowledge;
- merge two source claims into one record;
- convert an author’s population claim into a universal fact;
- copy proprietary charts, solver screenshots, exam spots or sequencing into product-facing material;
- use exam feedback as a replacement for missing lesson continuity.

Exact visual claims remain `VISUAL_PENDING` unless the visual is available and necessary.

## Evidence hierarchy

Use this authority order:

1. canonical source record;
2. source-family registry and gap ledger;
3. source-specific evidence matrix;
4. remaining-source question matrix;
5. heuristic candidate registry;
6. candidate-to-module validation workbench;
7. provisional final-rule slots;
8. adaptive readiness manifest;
9. learner and field evidence;
10. Playbook admission.

Source completeness does not imply strategic admission.

## Stable identities

Do not rename casually:

- source IDs;
- heuristic candidate IDs;
- misconception IDs;
- `LCM-01` through `LCM-11`;
- original drill IDs;
- learner-state dimensions;
- relation vocabulary;
- remaining-source question IDs.

A wording improvement does not justify a new ID.

## Incremental source-batch procedure

Treat each incoming package as a bounded transaction:

1. inventory all files;
2. identify exact duplicates before ingesting;
3. calculate checksum and perform technical QA;
4. create immutable source records only for new material;
5. update the source registry and gap ledger;
6. write one batch QA artifact;
7. write one bounded cross-source delta;
8. update only affected evidence/question/candidate/module rows;
9. create original drills or assessments only when the answer key is stable;
10. update bootstrap state when the milestone materially changes.

Default mutation level is evidence or explanation, not architecture.

## New-candidate gate

Before creating a new core candidate, prove that the idea is not merely:

- confirmation;
- simplification;
- boundary;
- context split;
- anchor detail;
- opponent/environment overlay;
- drill improvement;
- prerequisite explanation.

## Progress preservation

When a module changes:

- wording-only: preserve learner state;
- simplified: preserve state and add one confirmation variant;
- extended: preserve old-scope mastery, mark the new branch untested;
- context split: split mastery by context;
- revised: make affected mastery provisional and assign repair;
- rejected: create an explicit migration record.

Do not reset progress globally.

## Working style

- Use one active milestone at a time.
- Prefer the highest-EV bounded action.
- Avoid broad refactors, opportunistic cleanup and scope drift.
- Do not read the entire repository when the active authority cone is sufficient.
- Preserve accepted state unless evidence requires change.
- Distinguish fact, source claim, inference, hypothesis and field observation.
- Never fabricate closure.
- Stop when the next change is merely stylistic or depends on missing evidence.

## Required output after a batch

Return a compact operational report containing:

- package and checksum;
- duplicate/new-file split;
- source IDs created;
- technical QA and rerun verdict;
- strategic delta;
- conflicts/context splits;
- candidate count effect;
- drill/assessment effect;
- remaining coverage;
- exact files/commits;
- terminal verdict;
- next bounded action.
