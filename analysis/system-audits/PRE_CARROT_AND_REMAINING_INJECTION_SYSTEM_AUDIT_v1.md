# Live Cash System — Pre-Carrot and Remaining-Injection Deep Audit v1

Date: 2026-08-05  
Status: `SYSTEM_ARCHITECTURE_SOUND / PRECOMPUTATION_WAVE_COMPLETE`

## Scope

This audit evaluates the current system after:

- complete canonical ingestion and mapping of Smash Live Cash;
- complete canonical ingestion and mapping of all 30 FTGU episodes;
- canonical ingestion of Cash Injection Episode 01;
- activation of the adaptive module graph, learner-state schema and runtime;
- creation of 34 heuristic candidates, 30 misconception classes and initial original drills.

Remaining planned source work:

- Cash Injection Episodes 02–10;
- Carrot Poker Grade 1;
- Carrot Poker Grade 2;
- Carrot Poker Grade 3.

The purpose is to reduce future integration time without freezing content that still requires source validation.

## Executive verdict

The repository does not need another global restructuring.

Its major architectural boundaries are correct:

```text
source-faithful corpora
→ source analysis
→ candidate mechanisms
→ cross-source relations
→ stable adaptive modules
→ learner state and runtime
→ provisional Playbook
→ field validation
```

The remaining risk is not directory structure. It is coordination debt:

1. candidate-to-module ownership was implicit;
2. unresolved validation questions were distributed across multiple files;
3. drill, range and field-readiness were not visible in one manifest;
4. future source impact could still be over-processed without a freeze/mutation policy;
5. several early product snapshots contain stale status language but remain useful historical artifacts.

This audit closes items 1–4 through new SSOT artifacts. Historical snapshots are not rewritten unless they are active authorities.

## Current weaknesses and bounded remedies

### 1. Candidate registry is richer than the learner-facing map

There are 34 candidates but only 11 stable module families. This is intentional, but explicit ownership is required so later consolidation does not become a manual rediscovery exercise.

Remedy:

- `synthesis/CANDIDATE_TO_MODULE_VALIDATION_WORKBENCH_v0_1.md`

### 2. Validation dependencies are fragmented

Dependencies currently appear in:

- candidate registry notes;
- FTGU matrix;
- Cash Injection matrix;
- source ledgers;
- provisional Playbook caveats;
- route blockers.

Remedy:

- `synthesis/REMAINING_SOURCE_QUESTION_MATRIX_v1.md`

This file defines the exact questions remaining sources should answer. Incoming lessons are matched to questions, not merely summarized.

### 3. Module readiness is not one-dimensional

A mechanism can be source-ready but not drill-ready, anchor-ready or field-ready.

Remedy:

- `learning/ADAPTIVE_MODULE_READINESS_MANIFEST_v0_1.md`

The manifest separates:

- mechanism readiness;
- explanation readiness;
- boundary readiness;
- drill coverage;
- exact-anchor dependency;
- exploit evidence;
- field-transfer readiness.

### 4. Premature refinement risk

There is a temptation to polish final wording, ranges and exploit frequencies before Carrot and the remaining Injection episodes arrive.

Remedy:

- `governance/PRE_FINALIZATION_FREEZE_AND_MUTATION_POLICY_v1.md`

The policy freezes stable IDs and architecture while allowing bounded evidence and drill improvements.

### 5. Active versus historical artifacts

The provisional Playbook and fixed route remain useful snapshots but contain older status language. They should not be repeatedly rewritten as source state changes.

Authority rule:

- active navigation: adaptive route/runtime;
- active strategy inventory: candidate registry and evidence matrices;
- provisional Playbook: reasoning snapshot, not current validation authority;
- fixed route v0.1: historical curriculum snapshot.

## What can be safely improved before new sources

Safe now:

- candidate-to-module mapping;
- validation-question routing;
- module readiness accounting;
- direct-drill gap identification;
- source intake templates;
- conflict and context-split slots;
- progress-preserving version rules;
- environment evidence schema;
- original non-exact contrastive drills for robust mechanisms;
- stale-status cleanup in active authority files only.

Unsafe or low-EV now:

- final 14–18-rule wording;
- exact preflop charts;
- final exploit frequencies;
- broad population conclusions;
- fixed deep-stack thresholds;
- final module graduation thresholds;
- visual review of every course screen;
- aesthetic rewriting of canonical source records;
- replacing stable module IDs.

## Expected future integration transaction

For every incoming Cash Injection or Carrot batch:

```text
1. package QA and duplicate check
2. canonical source records
3. extracted mechanisms and claims
4. match to unresolved-question IDs
5. relation classification
6. candidate/module delta
7. drill or boundary delta only where warranted
8. update readiness manifest
9. update source registry
10. no unrelated rewrite
```

This should reduce each future batch to a bounded evidence transaction rather than a repository-wide analysis wave.

Risk: repeated wording and structure work creates no additional correctness.

Control: freeze/mutation policy and explicit deferred items.
